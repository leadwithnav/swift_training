## 🎯 Objectives
In this lab, you will:
1. Deploy MongoDB as a **StatefulSet** with a **Headless Service** and **`volumeClaimTemplates`**.
2. Observe stable network identities (`mongodb-0`, `mongodb-1`, `mongodb-2`) and stable DNS endpoints.
3. Observe how `volumeClaimTemplates` provisions dedicated storage for each pod ordinal.
4. Discover why bare StatefulSets **still leave a major gap** for production database management (lack of automated replication, failover, and day-2 operations).

## 🛠️ Step 1: Deploy MongoDB as a StatefulSet

Inspect `mongodb-headless-service.yaml` and `mongodb-statefulset.yaml`:

```bash
cd ~/swift_training/kubernetes/Lab9B
kubectl apply -f mongodb-headless-service.yaml
kubectl apply -f mongodb-service.yaml
kubectl apply -f mongodb-statefulset.yaml
```

Check the status of the StatefulSet and Pods:

```bash
kubectl get statefulset
kubectl get pods -w
```

Notice the **ordered deployment**:
- `mongodb-0` is created first and reaches `Running` before `mongodb-1` starts.
- `mongodb-1` reaches `Running` before `mongodb-2` starts.

### 🔹 2. Dedicated Storage Per Pod
Inspect the PersistentVolumeClaims dynamically generated by `volumeClaimTemplates`:

```bash
kubectl get pvc
```

Output:
```text
NAME             STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS
data-mongodb-0   Bound    pvc-11111111-2222-3333-4444-555555555555   1Gi        RWO            standard
data-mongodb-1   Bound    pvc-66666666-7777-8888-9999-000000000000   1Gi        RWO            standard
```

Each pod gets its **own dedicated PVC** bound strictly to its ordinal index (`0`, `1`, `2`)!

## 🔍 Step 3: Verify Stable DNS Network Identity

Test stable DNS resolution using the Headless Service (`clusterIP: None`):

```bash
kubectl run dns-test \
  --image=busybox:1.36 \
  --restart=Never \
  --rm -it \
  -- nslookup mongodb-0.mongodb-headless.default.svc.cluster.local
```

*Observation*: Headless DNS returns the individual IP addresses of all underlying pods.

## 🔍 Step 4: Test Pod Deletion & Re-attachment

Delete `mongodb-0`:

```bash
kubectl delete pod mongodb-0
kubectl get pods -w
```

*Observation*:
1. The new pod is named **`mongodb-0`** (NOT a random hash!).
2. It automatically re-attaches to **`data-mongodb-0`**, preserving all data stored prior to the deletion!

## ❓ The Critical Question: Why is a StatefulSet STILL NOT Enough for Databases?

You now have 3 pods: `mongodb-0`, `mongodb-1`, and `mongodb-2`.

Run a test command inside `mongodb-0` to check if database replication is active:

```bash
kubectl exec -it mongodb-0 -- mongo --eval "rs.status()"
```

Output:
```text
{
	"ok" : 0,
	"errmsg" : "not running with --replSet",
	"code" : 94
}
```

### 🚨 The Hidden Catch of Bare StatefulSets:
1. **No Database Replication**: StatefulSet manages Kubernetes pods and volumes, but it **does NOT configure database-level clustering** (e.g. `rs.initiate()` in MongoDB, `patroni` in Postgres, or master-replica sync in MySQL).
2. **No Automatic Primary Failover**: If `mongodb-0` crashes, the database does NOT automatically promote `mongodb-1` to primary at the database layer.
3. **No Automated Backups / Restores**: StatefulSets cannot take point-in-time database snapshots or manage WAL logs.
4. **No Zero-Downtime Database Upgrades**: Schema migrations and version upgrades require manual DBA scripts.

---

## 💡 Summary: Deployment vs StatefulSet

| Feature | Deployment (Lab 9A) | StatefulSet (Lab 9B) |
| :--- | :--- | :--- |
| **Pod Name** | Random (`dep-xyz12`) | Deterministic (`mongodb-0`, `mongodb-1`) |
| **Network Identity** | Ephemeral IP | Stable DNS (`pod-0.service.ns.svc.cluster.local`) |
| **Storage** | Shared PVC / Conflict | Dedicated PVC per pod (`data-mongodb-0`) |
| **Scaling Order** | Unordered | Sequential (0 ➡️ 1 ➡️ 2) |
| **DB Clustering & Day-2 Ops** | ❌ None | ❌ **None (Requires Manual DBA Steps)** |
